# Approved AFL knowledge library

## Intent and authorization
The user approved implementation of the proposed private, curated knowledge library with WhatsApp submissions, explicit publishing, versions, expiry, audience controls, and grounded answers. Their standing instruction approves plans without another pause. Implement in the existing bot repository and dedicated Dokploy service only. Keep WhatsApp unpaired and the member test allowlist unchanged.

## Architecture
Keep neonize, Groq, Graphiti/FalkorDB, and the public Top100 activities integration. Add a standard-library SQLite catalog beside the persistent WhatsApp session. This catalog records authoritative content and its publishing lifecycle; Graphiti remains conversation memory but cannot confer official authority on ordinary chat or old bot answers. No Top100 backend or schema changes and no new dependencies.

## Intake and publishing
Admin DMs accept `knowledge draft <title> | audience=members|admin_only | effective=<ISO date/time> | expires=<ISO date/time> | replaces=<id> | source=<https URL>`, followed by a newline and content. All options are optional; audience defaults to admin_only. Dates without times mean midnight Africa/Lagos; timestamps require a timezone. Reject unknown options, invalid intervals, empty content, and content above 80,000 characters. A maximum 10 MB PDF can be submitted in admin DMs or the optional knowledge group; its extracted text is a draft, never immediately published. Scanned/empty documents get a clear rejection.

`KNOWLEDGE_GROUP_JID` is an optional, exact single group ID separate from the member test group. Only configured ADMIN_PHONES/ADMIN_JIDS senders can submit there; commands and plain text from those senders create/manage drafts. Other senders are dropped before recording or logging content. Feed acknowledgements and previews are sent privately to the submitting admin. Feed messages never enter recent context, Graphiti, summaries, or the public PDF pool.

Admin commands: `knowledge help`, `knowledge list`, `knowledge show <id> [page]`, `knowledge publish <id>`, and `knowledge retire <id>`. Draft creation returns its ID, audience, dates, replacement, provenance, and a content preview. Full content is available through paged show. Explicit publish constitutes approval. Legacy `ingest <text>` and automatic admin ingestion create drafts in library mode, not verified Graphiti facts. Enforce authorization again at the runtime boundary, not in prompts. Ordinary DMs cannot invoke management.

Implementation refinement: `knowledge audience <id> members|admin_only` classifies an existing draft and returns an updated preview. This makes plain feed/PDF submissions usable for members without publishing private defaults accidentally. Published audiences cannot be changed in place.

## Lifecycle and access
Draft/published/retired status; immutable content after publication. Save creator, source chat/message/file, timestamps, publisher, and audit events. Replay of the same source chat/message ID is idempotent. A replacement must reference a published predecessor of the same audience. Publishing atomically schedules the predecessor's supersession at the replacement's effective time; publishing concurrent replacement drafts fails. Before that time the old entry remains active. Once superseded, retired, or expired, entries never reappear implicitly. Replacement chains remain viewable for audit.

Only published, effective, unexpired, unsuperseded member entries can be retrieved for member groups/DMs. Admin-only entries are available exclusively in authenticated admin DMs, never in groups even if an admin asks. Revocation and dates are checked on each retrieval and again after the model call before sending. PDFs persist in the catalog and downloads apply the same access rules. Ambiguous document requests list accessible matches privately/in the originating chat instead of sending an arbitrary latest PDF.

## Answer grounding
Library mode is on by default. Candidate excerpts come from active approved entries, read-only current public Top100 activity records, or fixed bot capability facts. Chat history can resolve the topic but is not evidence for official facts. Groq returns JSON selecting exact excerpts by source ID, with explicit unknown/conflict signals. The application validates IDs and verbatim substring matches, rejects malformed/unsupported output, bounds excerpts and response size, and attaches source labels/links itself. No free-generated factual prose is sent through this path. Unknown/conflicting answers stay silent in member groups and notify admins through the existing mechanism. Disable automatic fact corrections from ordinary Graphiti memory in this mode. Existing `/summary` and reminder skills remain conversational records/actions; the knowledge feed never enters their inputs.

## Persistence, rollout and verification
Derive knowledge.sqlite3 from WHATSAPP_SESSION_PATH's parent unless KNOWLEDGE_DB_PATH is explicit. Existing /app/data volume persists both metadata and PDFs. Add KNOWLEDGE_LIBRARY_ENABLED=true and an empty KNOWLEDGE_GROUP_JID to .env.example; leave user credentials and JIDs untouched. Feature flag false preserves legacy behavior for compatibility, but is not the recommended deployment.

Use focused real SQLite and runtime tests for draft/publish, expiry boundaries, replacement scheduling/races, restart persistence, audience and sender isolation, replay protection, PDF access, invalid model evidence, stale sources during generation, and unavailable model/API behavior. Run the repository test suite and config readiness check. Publish code to the existing bot branch and redeploy only its dedicated service, verifying deployment status and metadata-only logs. Credentials, QR pairing, and admin/member group IDs remain user actions when unavailable.
